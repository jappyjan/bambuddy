My read: A, because the thing SimplyPrint actually got right is that the detail view is cheap to open and cheap to abandon — you skim a folder by clicking, and the Slice button is always in the same place. Your page already has the resizable sidebar and the lg: breakpoints this needs, so the panel is additive rather than a rewrite. B is the least code of the three but the grid jumping around under your cursor gets old fast, and there is nowhere to put a 3D preview. C is the most room to grow and the only deep-linkable one — but every folder skim becomes navigate-in, navigate-out.

Multi-select is on, so if you want e.g. A on desktop and C on phone (panel on big screens, real screen on small ones), click both — that combination is a legitimate answer and honours your “different views per screen size” ask.

The desktop layout is more or less dictated by the reference you sent, so I've drawn it once below — tell me if anything's wrong. The real open question is the phone, and that's the A/B/C choice at the bottom.

Proposed desktop layout

Left rail = the preset triplet on top, then the parameter editor fed by the 102 fields already sitting in process_fields.json — Basic / Advanced tiers, a search box, category chips matching that file's own categories. Overridden values get an amber dot and are the only ones sent to the backend. Viewport owns the space; placement gizmos left, plate tabs top-left, transform readout bottom-right. Bottom bar: estimate, then Slice, then Print now lights up once a slice exists — no bouncing back to the file manager.

Phone: three strategies

You asked for “more menu focused on phones”. These differ in how far they let go of the desktop shape to get there.

A

Bottom tabs

Plate is a full-bleed viewport with big touch gizmos. Settings is a native-feeling drill-down list — tap Quality, get its fields, tap back. Print is the summary and the two buttons. Each tab gets the whole screen at the density it wants.

My read: A. It's the only one where the 3D view gets the entire screen when you want it and the settings get a proper full-height list when you want that — which is exactly the “3D-centred on desktop, menu-centred on phone” split you described, without a compromise in the middle. It's also the cheapest to build honestly: the tabs render the same three components the desktop rail and stage already render, just at one-per-screen instead of side-by-side. B looks like less work but a drag-divider over a WebGL canvas is fiddly on touch, and you end up with two cramped panes instead of one good one. C is the most beginner-proof and the most annoying for the 90% case of re-slicing a file you've sliced before.

Multi-select is on if you want to say “A, but borrow C's filament step”.
