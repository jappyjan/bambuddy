# Spike #70 — where does an STL actually land?

**Date:** 2026-08-07 · **Ticket:** #70 (`bed.0`), epic #67 · **Branch:** `bed-0-stl-spike`

This is the results file the #22 spike never wrote — the omission that made #70
necessary. Numbers below come from G-code produced by the **deployed** sidecar,
not from reasoning. Raw scripts sit alongside this file; `run_placement_spike.sh`
reproduces the whole matrix in about a minute.

## What was measured against

| | |
|---|---|
| Host | `printfarm` (NixOS, podman), reachable on the LAN and the tailnet |
| Sidecar | `http://printfarm:3000` — `ghcr.io/jappyjan/orca-slicer-api@sha256:2e2d9cfe…`, **OrcaSlicer 2.3.2**, `/health` green |
| App | `http://printfarm/` — `ghcr.io/jappyjan/bambuddy@sha256:bf267abb…`, built from `slicer-ux-redesign` @ **`b4ae21d2`** |
| Wire payload | the `{name, inherits, from:"system", type}` stubs `_resolve_standard` emits (`backend/app/services/preset_resolver.py:254`), i.e. byte-identical to a real "Standard"-tier slice |
| Method | HTTP only. No container, registry or database command was run. |

**BambuStudio was not measured.** The deployed sidecar is OrcaSlicer; reaching
`bambu-studio-api` would have meant running a container, which this session was
forbidden from doing. Every "the slicer" statement below therefore means
*OrcaSlicer 2.3.2*, and the #22 claims that name BambuStudio specifically remain
unverified — see "Not measured" at the end.

## Models

Generated by `mkmodels.py`; deliberately asymmetric so a rotation cannot hide.

| model | STL bbox | why |
|---|---|---|
| `bar.stl` | `(0,0,0)…(60,20,10)` | the #22 shape. 90° rotation flips the bbox to 20×60 |
| `bar_offset.stl` | `(40,25,0)…(100,45,10)` | same bar, translation baked into the vertices |
| `ell.stl` | `(0,0,0)…(60,50,10)` | an L. One bbox quadrant is empty, which survives translation and names the rotation |
| `pair.stl` | two bars 150 mm apart in Y | a gap `--arrange` would close |
| `far_pair.stl` | two bars 300 mm apart, bbox 60×320 | does not fit a 256 bed unless something repacks it |

Placement is read off the first layer only, skipping Custom/skirt/brim so the
A1's purge line at X = −48 does not pollute the box (`gcode_shape.py`).

## 1. Where does the object land? — **Bed centre, exactly.**

| slice | first-layer min | max | **centre** | size |
|---|---|---|---|---|
| `bar` → A1 | (98.325, 118.325) | (157.675, 137.675) | **(128.000, 128.000)** | 59.35 × 19.35 |
| `bar_offset` → A1 | (98.325, 118.325) | (157.675, 137.675) | **(128.000, 128.000)** | 59.35 × 19.35 |
| `ell` → A1 | (98.325, 103.325) | (157.675, 152.675) | **(128.000, 128.000)** | 59.35 × 49.35 |
| `pair` → A1 | (98.325, 43.325) | (157.675, 212.675) | **(128.000, 128.000)** | 59.35 × 169.35 |

128.000 is exactly half of the A1's 256 mm bed. The ~0.325 mm inset per side is
half an extrusion width — these are toolpath centrelines, so a nominal 60 mm
edge measures 59.35.

**The baked-in translation is discarded completely.** `bar` and `bar_offset`
differ in the mesh by (+40, +25); their G-code differs by **200 comment lines**
naming the source file and **zero motion commands**. Not "close" — every `G0`/`G1`
is byte-identical.

`pair` shows this is bounding-box centring, not per-object centring: the 150 mm
gap between the two bars is preserved and the *pair's* bbox is centred.

> Confirms the #22 finding for OrcaSlicer. An STL already slices dead centre
> today, with no help from Bambuddy.

## 2. Is orientation preserved? — **Yes, on OrcaSlicer.**

* `bar` slices 59.35 in X by 19.35 in Y. The long axis is still X. A 90° rotation
  would have produced 19.35 × 59.35.
* `ell`'s empty quadrant is `+x+y` in the G-code, which is where it is in the
  mesh. Rotation would move it to `-x+y` (90° CCW), `-x-y` (180°) or `+x-y`
  (90° CW). Quadrant fractions: `+x+y` 0.000, `-x+y` 0.292, `-x-y` 0.354,
  `+x-y` 0.354.

The same signature holds on the A1 mini, so it is not printer-specific.

> **This does not contradict #22.** #22's rotation claim was about *BambuStudio*
> ("a 60x20 bar comes out of BambuStudio rotated 90 degrees"), which is not what
> the deployment runs. What is new is that **the defect #71 was partly written to
> chase does not exist on the sidecar the owner is actually testing against.**

## 3. Does the slice match the `/slicer` preview?

**On the deployed build there is no preview to match.** The deployed bundle
(`http://printfarm/assets/index-DeS8C4X4.js`) still contains

```js
ot={url:rt,fileType:T.length>0?`3mf`:void 0, plates:L, …}
```

— the pre-#66 line. `platesMeta.length` is 0 for an STL, so `fileType` is
`undefined`, `ModelViewer` cannot classify an extensionless download URL, and
`/slicer` renders **"unsupported file format"**. That is exactly the bug fixed by
`273eb318` ("tell the viewer an STL is an STL", #66), merged into
`slicer-ux-redesign` at `e018c336` on 2026-08-07 — *after* the image was built
from `b4ae21d2` on 2026-08-04.

**The owner's round-4 complaint was formed against a build that showed no STL at
all.** Any reasoning about "the preview disagrees with the result" has to account
for that.

With #66 applied, reading `ModelViewer.tsx` at `e018c336`:

* `shouldCenterOnPlate = isStlModel` is unconditionally true for an STL
  (`:673`), so the preview places it at `-center + buildVolume/2` (`:715-717`) —
  **dead centre of the plate, the same rule the slicer applies.**
* The STL branch applies `geometry.rotateX(-Math.PI/2)` only (`:476`) — Z-up to
  Y-up. No Z rotation, so the preview's orientation matches the slice.
* `buildVolume` falls back to `DEFAULT_BUILD_VOLUME {256,256,256}` — visible in
  the deployed bundle twice, as `xoe` and `Q0e`.

So the relationship is:

| target printer | preview object | sliced object | agree? |
|---|---|---|---|
| A1 / X1C / P1S / P1P (256×256) | centre of a 256×256 plate | (128.000, 128.000) | **exactly** |
| A1 mini (180×180) | centre of a **256×256** plate | (90.000, 90.000) on a 180×180 bed | object is centred in both; **the drawn plate is the wrong size** |

**The object is never mis-placed relative to its bed. The bed itself is drawn
wrong.** That is #69's ticket, not #71's.

## 4. Does it differ per printer profile? — **Yes. The slicer already honours the target bed.**

| printer | `printable_area` in the G-code header | measured centre | = bed/2? |
|---|---|---|---|
| Bambu Lab A1 0.4 | `0x0,256x0,256x256,0x256` | (128.000, 128.000) | yes |
| Bambu Lab A1 mini 0.4 | `0x0,180x0,180x180,0x180` | **(90.000, 90.000)** | yes |

Same `ell.stl`, same stub shape, only the printer name changed — and the part
moved to the new bed's centre. **The slice output already follows the selected
printer.** Nothing in Bambuddy needs to learn the bed size for the *G-code* to be
right; the bed size is needed for the *viewport*.

Useful side note for #68: the produced G-code **declares `printable_area`
verbatim in its header**. That is a real second source for the number — but only
*after* a slice, so it cannot feed a pre-slice viewport. It is a cheap way to
assert #68's values in a test, not a substitute for the sidecar change.

### A blocking defect found while doing this

**A bare STL cannot be sliced at all for most Bambu printers on the deployed
sidecar.** Reproducible, printer-family specific, not load-induced:

| printer | result |
|---|---|
| A1 0.4, A1 mini 0.4 | HTTP 200 |
| X1 0.4, X1 Carbon 0.4, P1P 0.4, P1S 0.4, P2S 0.4, H2D 0.4, H2S 0.4 | **HTTP 500, `Slicer process failed (signal SIGSEGV)`** |

Isolation performed:

* Retried one at a time, 20 s apart, interleaved with a passing A1 slice — the
  A1 succeeded between two X1C failures. Not memory pressure or concurrency.
* Independent of the process preset (`0.20mm Standard @BBL X1C` and
  `0.16mm Optimal @BBL X1C` both crash).
* Independent of the model (a plain 20 mm cube crashes on H2D, succeeds on A1).
* **Crashes with `exportType=3mf` too**, so it happens before G-code generation —
  it is in profile resolution / model load, not the toolpath pipeline.

Not isolated further: naming the faulty key would need to read the resolved
profile inside the container, and container commands were out of scope. This is
almost certainly worth its own ticket — it blocks the epic's own acceptance
("a non-square bed renders non-square" cannot be checked end to end, because the
only non-square bed here is the H2D's 350×320 and the H2D cannot slice an STL).

## 5. Does `--arrange` change anything? — **No. It is a measured no-op.**

`arrange=true` was sent as a form field, exactly as `slicer_api.py:322-328` does.

| pair | G-code bodies |
|---|---|
| `bar_offset` vs `bar_offset --arrange` | **identical** (408,888 bytes each) |
| `ell` vs `ell --arrange` | **identical** (552,748 bytes each) |
| `pair` (150 mm gap) vs `pair --arrange` | **identical** (686,717 bytes each) — the gap is *not* closed |

And the decisive one: `far_pair.stl` has a 60 × 320 bbox that cannot fit a
256 × 256 bed unless something repacks the two bars. Both with and without
`--arrange` it fails identically:

```
HTTP 500 — "One of the plate is empty or has no object fully inside it."
exit code 206 — plate 1: Nothing to be sliced
```

If `--arrange` were doing anything, this is the case it would rescue.

**Caching ruled out:** every response carries its own
`; generated by OrcaSlicer 2.3.2 on … at HH:MM:SS` stamp matching its request
time, so each arrange/no-arrange pair is two genuinely separate slicer runs that
happened to produce identical bytes.

*What cannot be told apart from outside:* whether the sidecar declines to forward
the flag to OrcaSlicer (`slice_with_profiles`' docstring describes `--arrange` as
a BambuStudio flag) or whether OrcaSlicer accepts and ignores it. Either way the
**observable** answer is the same: flipping the `library.py:3903` gate for STLs
would change nothing on this deployment.

## Bonus: the `ensure_project_3mf` cost #71 asks about

Same model, same profiles, warm sidecar, three runs each:

| request | times |
|---|---|
| normal G-code slice | 0.324 s, 0.325 s, 0.401 s |
| `exportType=3mf` | 0.330 s, 0.399 s, 0.323 s |

An export costs the same as a slice, so #71's "doubles slice time" is
**structurally true** — but the constant is ~0.33 s for a small part on this
host, not minutes. #71 still needs to measure it on a *realistic* model; this
number only establishes that the two calls cost the same, which is the part that
makes the doubling exact.

## Recommendation

**#71 does not survive as written, and should not be built as specced.**

Its premise is that an STL needs a synthetic plate so Bambuddy can place and
centre it. The measurements say Bambuddy has nothing to fix there:

1. The slicer already centres a bare STL, exactly, discarding any baked placement.
2. It already centres onto the **target printer's** bed, not a default one.
3. It already preserves orientation (on OrcaSlicer, which is what runs).
4. `ModelViewer`'s STL branch already centres the preview on the plate by the
   same rule, so preview and slice already agree on placement and orientation.

Everything the owner can actually see that is wrong reduces to **one** thing: the
plate is drawn 256×256 no matter which printer is selected. That is **#69**, and
#69 needs **#68**. Neither needs a synthetic plate.

Concretely:

* **#71 shrinks to nothing placement-related.** What is left is optional and
  should be re-scoped or closed: giving an STL objects would light up the
  transform gizmos (today `nodes: []` leaves a permanent "This plate has no
  objects" beside a live toolbar), which is a *manual-placement* feature — a
  different, unrequested want. If the owner does ask to drag an STL around a
  plate, `ensure_project_3mf` + `apply_plate_layout` are the right machinery and
  the ticket can be rewritten then. Do not build it to fix centring.
* **The `--arrange` escape hatch in #67 should be struck**, not deferred. It is
  measured to do nothing on this deployment, and it was only ever a way to buy
  centring the slicer already does for free.
* **#66 must reach the deployment before any of this is re-tested.** The image
  predates the fix, so the owner has never seen an STL preview. Re-testing #67's
  premise on `b4ae21d2` will keep producing misleading feedback.
* **Raise the SIGSEGV separately.** "Slice an STL for anything that is not an A1"
  is broken on the deployed sidecar, and it also blocks #69's acceptance criterion
  about non-square beds.

## Not measured — stated plainly

* **BambuStudio.** Only OrcaSlicer 2.3.2 was reachable without a container
  command. #22's specific rotation claim is about BambuStudio and is neither
  confirmed nor refuted here. If Bambuddy can be configured to prefer
  BambuStudio, the orientation question is still open for that path.
* **A non-square bed.** The only non-square bundled bed in reach is the H2D's
  350×320, and every H2D STL slice SIGSEGVs. So "does the slicer centre correctly
  on a non-square bed" is **undetermined**. Both measured beds were square
  (256×256, 180×180).
* **The end-to-end app path.** `http://printfarm/api/*` requires authentication
  and this session did not authenticate. Slices were driven against the sidecar
  with the payload Bambuddy's own `_resolve_standard` builds, which is the same
  wire request minus the app's HTTP wrapper — but it is not literally a click in
  the UI.
* **Whether `--arrange` reaches the OrcaSlicer CLI.** Only its (null) effect was
  observed; the argv could not be inspected without entering the container.
* **The live library files** (file 31 `Hub.stl`, file 2 `Attractap - floor
  (desk).stl`) were never fetched, for the same auth reason. Purpose-built
  asymmetric parts answer the questions better anyway — `Hub.stl` sounds
  rotationally symmetric, which would have hidden exactly the defect being
  hunted.
